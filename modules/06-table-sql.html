Module 06

Table API & Flink SQL

Not every pipeline needs hand-written operators. The Table API and Flink SQL let you describe the same streaming and batch logic declaratively — and Flink's planner figures out the operator graph for you.

New to this? Start here. A normal SQL query is like asking a librarian once, "how many books are checked out right now?" — you get one answer, and that's the end of it. A streaming SQL query is like asking that librarian to stand there and call out an updated count every single time a book is checked out or returned, forever, without you ever having to ask again. Same SQL syntax you may already know — a fundamentally different, never-ending kind of answer.

Why offer SQL when Module 03 already gave us an API?

Two reasons. First, far more people already know SQL than know Flink's Java/Python APIs — data analysts, backend engineers, anyone who's ever queried a database can write a streaming pipeline without learning a new library. Second, SQL is declarative: you say what result you want, and Flink's query planner works out the most efficient way to compute it — sometimes better than a hand-written pipeline, the same way a database query planner can outsmart a hand-rolled loop over rows.

In fact, the word-count example from Module 03 (keyBy(...).sum(...)) and the SQL query below solve the same problem — a running total per group, updated forever — just in two different languages for describing it.

The same engine, a declarative face

Flink SQL runs on the exact same runtime as the DataStream API — it compiles down to operators, state, and watermarks just like the code in Module 03. A streaming SQL query keeps running continuously, emitting updated rows as new events arrive, the same way the keyBy().sum() example did. 

CREATE TABLE orders (
  id INT,
  customer STRING,
  category STRING,
  amount DOUBLE,
  order_time TIMESTAMP(3),
  WATERMARK FOR order_time AS order_time - INTERVAL '5' SECOND
) WITH (
  'connector' = 'kafka',
  'topic' = 'orders',
  'format' = 'json'
);

SELECT category, SUM(amount) AS total
FROM orders
GROUP BY category;

In plain words: the CREATE TABLE part just tells Flink "here's what a row of order data looks like, and here's where to actually read it from" (a Kafka topic, in this case). The WATERMARK FOR ... line is the interesting part — see the callout below. The SELECT ... GROUP BY category underneath is the actual query — and unlike a spreadsheet formula that computes once, it keeps re-emitting an updated total every time a new order for that category arrives.

The WATERMARK FOR ... clause is exactly the watermark idea from Module 04 — "how patient should Flink be with orders that show up a little late" — just written as part of the table's schema (SQL DDL) instead of a WatermarkStrategy object in code.

Table API: the programmatic equivalent

Sometimes you don't want a raw SQL string in your code — maybe you want autocomplete, type-checking, or to build a query piece-by-piece based on some condition. The Table API is the same idea as the SQL above, just written as chained method calls instead of a string: 

Table result = tableEnv.from("orders")
    .groupBy($("category"))
    .select($("category"), $("amount").sum().as("total"));

This compiles to the exact same execution plan as the SELECT category, SUM(amount) ... GROUP BY category query above — Table API and SQL are two spellings of the same thing. You can freely mix both with each other and with the DataStream API (Module 03) in the same job, converting back and forth wherever it's convenient.
