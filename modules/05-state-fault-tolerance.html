Module 05

State & Fault Tolerance

Flink jobs run for weeks or months, and machines fail during that time. State and checkpointing are what let a job pick up exactly where it left off — without losing or double-counting a single event.

New to this? Start here. Think of a video game with no save feature: if it crashes an hour in, you're back to the very start — all that progress just gone. A game with autosave is different: it crashes, you reload the last save, and you're back in business a minute later, not an hour. Flink's "state" is your job's progress (running counts, what it's seen so far); a "checkpoint" is the autosave. Everything below is really just: what gets saved, and how the autosave works.

Why does a streaming job even need "saves"?

Picture a job counting how many times each user has viewed a page today — a running total per user that lives entirely in memory while the job runs. Now a server hosting part of that job crashes. Without any saved progress, you have two bad options: wipe all counts back to zero (you just lost real data), or somehow guess what to keep (you risk counting some views twice). Neither is acceptable for a job that's supposed to run for months. Checkpoints are how Flink avoids that dilemma entirely — it always has a recent, trustworthy save to reload from.

Two kinds of state (two kinds of "progress" to save)

  • Keyed state — one value per key, like a scoreboard with a separate line for every player rather than one shared number. In Flink this is ValueState, ListState, or MapState, and it's what almost every stateful operator uses under the hood: a running count per customer, a session per device, a "have I seen this ID before" set for deduplication.
  • Operator state — not tied to any key at all, just tied to one worker's own progress, like a bookmark that says "I've read up to page 47" regardless of what's written on that page. The classic example is a Kafka source remembering "I've read up to message #4821 in partition 2," so after a restart it knows exactly where to resume reading.

Checkpoints: the autosave itself

Periodically, the JobManager sends a checkpoint barrier — think of it as a "save now" signal — flowing through the pipeline alongside the real data. As it passes each operator, that operator writes its current state to durable storage. Once every operator across the whole pipeline has confirmed its save, the checkpoint is complete: one consistent, whole-pipeline point-in-time snapshot to recover from — not a patchwork of saves taken at different moments.

On failure, Flink restarts the affected parts of the job from the latest completed checkpoint and replays source data from the position recorded in that snapshot (that's what the Kafka "bookmark" from operator state is for). Combined with a replayable source like Kafka and transactional sinks, this combination is what gives Flink its exactly-once guarantee: every event affects the result exactly once, crash or no crash.

Checkpoints vs. savepoints: a checkpoint is Flink's own automatic, frequent autosave, purely for failure recovery — you never trigger it by hand. A savepoint is more like manually typing "save" before doing something risky: you trigger it yourself before a planned operation — upgrading your job's code, changing its parallelism, or moving it to a different cluster — then resume the new version of the job from that exact point, with nothing lost.

State backends, briefly

While the job is running, state has to actually live somewhere on the worker — that "somewhere" is the state backend. Two options, with a trade-off you've probably made before with your own notes:

BackendLike...Trade-off
HashMapStateBackend Keeping it all in your head Very fast to access, but limited by how much fits (JVM memory) — fine for small-to-moderate state.
EmbeddedRocksDBStateBackend Writing it in a notebook on your desk Slightly slower per access, but holds far more than memory ever could — the usual choice once state gets large (millions of keys).

Either way, this local copy is just where state lives while running — checkpoints still back it up to durable remote storage (e.g. S3 or HDFS), which is what actually survives a machine being lost entirely.

How this is actually used in Flink

A common real case: flag a customer if they make more than 5 transactions in one minute (basic fraud detection). That "count in the last minute, per customer" has to survive restarts, or a well-timed crash would quietly reset everyone's count to zero — exactly the kind of state this module is about. 

public class FraudCheckFunction extends KeyedProcessFunction<String, Transaction, Alert> {
    // keyed state: one counter per customer ID, survives checkpoints and restarts
    private ValueState<Integer> recentCount;

    public void processElement(Transaction t, Context ctx, Collector<Alert> out) {
        int count = recentCount.value() == null ? 0 : recentCount.value();
        count++;
        recentCount.update(count);
        if (count > 5) out.collect(new Alert(t.customerId));
    }
}

recentCount is exactly the "scoreboard per player" keyed state from earlier. Because it's checkpointed automatically, a crash mid-job can't quietly reset a customer's count and let fraud slip through unflagged.
