Module 05

State & Fault Tolerance

Flink jobs run for weeks or months, and machines fail during that time. State and checkpointing are what let a job pick up exactly where it left off — without losing or double-counting a single event.

Two kinds of state

  • Keyed state — scoped to the current key on a keyed stream (ValueState, ListState, MapState). Used by almost every stateful operator: running counts, sessions, dedup sets.
  • Operator state — scoped to a parallel operator instance rather than a key. Used for things like source offsets (e.g. a Kafka consumer's per-partition read position).

Checkpoints: the safety net

Periodically, the JobManager injects a checkpoint barrier into the stream. As it flows through the graph, every operator snapshots its state to durable storage the moment the barrier passes. Once every operator has confirmed its snapshot, the checkpoint is complete — a consistent, whole-pipeline point-in-time you can recover from.

On failure, Flink restarts the affected operators from the latest completed checkpoint and replays source data from the recorded offsets. Combined with a replayable source (like Kafka) and transactional sinks, this is what gives Flink its exactly-once guarantee.

Checkpoints vs. savepoints: a checkpoint is automatic, lightweight, and managed by Flink for failure recovery. A savepoint is a manually triggered, portable snapshot you use for planned operations — upgrading your job code, changing parallelism, or migrating clusters — and then resume from.

State backends, briefly

State lives in a state backend while the job runs. The HashMapStateBackend keeps state as objects on the JVM heap (fast, but limited by memory); EmbeddedRocksDBStateBackend keeps state on local disk via RocksDB, spilling far beyond memory — the usual choice for very large state. Both checkpoint to a durable remote store (e.g. S3 or HDFS) regardless of which backend you pick.
