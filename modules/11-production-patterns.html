Patterns from a Real Job

Module 10 showed the infrastructure around a production job. This module looks inside one: a long-running enrichment job that merges about ten Kafka and Kinesis sources, keeps per-device records up to date, and calls external HTTP APIs when data needs refreshing. It has no windows and no watermarks, but it uses almost every other part of the DataStream API. Each section below covers one Flink concept the job depends on, and the reason it was chosen.

How to read this module. Names, topics and payloads are generic. The job itself is real, and the code snippets are simplified versions of how it is built. Each section ends with the mistake that concept protects against, because most of these patterns were introduced after that mistake had already happened in production.

1 · union(): many sources, one operator

Every source deserializes into the same envelope type: a trace context plus a Protobuf message with an eventType field. Because the types match, the job can union() eight streams into one and send them to a single keyed operator. That operator then holds one consistent view of each device. Without the union, the same device's state would be split across eight operators. 

var combined = statusStream;
if (profileStream != null)  combined = combined.union(profileStream);   // feature-flagged
if (contextStream != null)  combined = combined.union(contextStream);   // feature-flagged
if (refreshResults != null) combined = combined.union(refreshResults);  // loops back from async I/O

combined.keyBy(e -> e.f1.getDeviceId())
        .process(new StaticDataProcessor(...))
        .uid("staticDataProcessor");
  • union vs. connect: union needs identical types and gives you one stream. connect keeps two different types apart and gives you a CoProcessFunction with processElement1/2. Having one shared envelope type is what makes the simpler union possible.
  • Feature flags change the graph. When a source is disabled, its stream is null and it is never added to the graph at all. That is a change to the topology, not just a config change. Restoring from a savepoint still works because every operator has a stable uid(). If you remove a stateful operator, you need --allowNonRestoredState.
Mistake it prevents: two operators each keeping half of a device's record and overwriting each other's writes in the database.

2 · keyBy decides where state lives

The job keys the same data three different ways, and each key has a different purpose:

OperatorKeyWhy
Static processordeviceIdAll updates for one device go to one subtask, in order. Per-device state is consistent.
Global processorjobIdRecords that apply to many devices are grouped by the job they belong to.
Routerpartition → device → job → request ID (first one present)Mixed input: use whichever identifier the event actually has.
Token cacheeventTypeOnly about 7 distinct keys, so one cached token per downstream API.

The token cache shows an important rule: the number of distinct keys limits your useful parallelism. With 7 keys, at most 7 subtasks will ever do any work. The job sets this operator's parallelism to 1 for that reason.

The router's fallback key is valid, but it is deterministic only per event shape. An event keyed by Kafka partition "3" and another keyed by device "3" would land in the same key group and share state. Keep the key spaces separate, for example by prefixing "p:3" and "d:3", when one operator can receive several kinds of key.

Mistake it prevents: keying on something non-deterministic, such as a random value or a timestamp. Flink must compute the same key for a record every time; otherwise state ends up on the wrong subtask after a restore.

3 · Side outputs as a router

One KeyedProcessFunction looks at the eventSubtype and sends each event to one of several outputs. The event can go to the main output, the static side output, the refresh side output, or, if it throws, the DLQ side output. Downstream, the static processor sends results onward through one of three priority side outputs (P0/P1/P2), and each of those has its own Kinesis sink. 

public static final OutputTag<Envelope> STATIC  = new OutputTag<>("staticDataStream")  {};
public static final OutputTag<Envelope> REFRESH = new OutputTag<>("refreshDataStream") {};
public static final OutputTag<Envelope> DLQ     = new OutputTag<>("dlqStream")         {};

switch (event.getEventSubtype()) {
  case MAPPING_UPDATE        -> out.collect(event);              // main output
  case STATIC_DATA_UPDATE    -> ctx.output(STATIC, event);
  case PROFILE_REFRESH       -> { if (debounce.allow()) ctx.output(REFRESH, event); }
}

// in the job:
var routed  = combined.keyBy(...).process(new Router());
var refresh = routed.getSideOutput(REFRESH);
var statics = routed.getSideOutput(STATIC);
  • Why {} after new OutputTag? The empty braces create an anonymous subclass. Java erases generic types at runtime, and the subclass is how Flink still finds the element type Envelope. If you leave them out, you get an InvalidTypesException.
  • Why not filter() three times? Each filter evaluates every record again and needs its own state access. A side-output router reads state once and makes one routing decision for each event.
  • Priority lanes: separate sinks for P0/P1/P2 mean a backlog of low-priority traffic does not delay high-priority records on the same Kinesis stream. Each lane has its own buffer and its own in-flight request limit.
Watch out: a side output that nothing reads with getSideOutput() is discarded without any warning. If an operator writes failures to DLQ but the job graph never calls getSideOutput(DLQ) on that operator, those records are lost. Check that every ctx.output(tag, …) has a matching getSideOutput(tag).

4 · State TTL as a debounce

Refresh requests can arrive in bursts, for example 40 requests for the same device in a few seconds. Each one would trigger an HTTP call to an external API. The router stops this with a ValueState<Boolean> flag per (device, API) that has a TTL. If the flag is empty, the refresh goes through and the flag is set. If the flag is set, the refresh is dropped and a counter goes up. When the TTL expires, the flag disappears and the next refresh is allowed again. The same mechanism caches OAuth tokens: the TTL is set to the token's lifetime, so an expired token is never returned. 

var ttl = StateTtlConfig.newBuilder(Duration.ofSeconds(debounceSeconds))
    .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
    .build();
var desc = new ValueStateDescriptor<>("profileRefreshLimiter", Types.BOOLEAN);
desc.enableTimeToLive(ttl);

boolean allow() throws IOException {
  if (!Boolean.TRUE.equals(limiter.value())) { limiter.update(true); return true; }
  return false;
}
  • No timers needed. You could build this with registerProcessingTimeTimer + onTimer + clear(). TTL does the same thing in a few lines and also cleans up state for devices that never send another event.
  • OnCreateAndWrite vs. OnReadAndWrite is the setting that matters most here. If reads also reset the TTL, every dropped request (a read) extends the window. A device that sends a request more often than the TTL would then never be refreshed again. Try it in the simulator below.
  • TTL uses processing time (wall-clock time), not event time. That is what you want for rate limiting.

5 · Async I/O for external calls

A refresh needs an HTTP call that takes 50–500 ms. If that call blocks inside processElement, the subtask handles about 5 records per second, and backpressure slows every source down to that rate. AsyncDataStream allows many calls to be in flight at once from a single subtask: 

AsyncDataStream.unorderedWait(
        refreshWithToken.keyBy(e -> e.f1.getDeviceId()),
        new AsyncCaller(props),          // RichAsyncFunction
        operatorTimeoutMs, TimeUnit.MILLISECONDS)   // capacity defaults to 100
    .uid("asyncCaller");

// inside AsyncCaller
public void open(Configuration c) {
  http     = new OkHttpClient.Builder().callTimeout(httpTimeoutMs, MILLISECONDS).build();
  executor = Executors.newFixedThreadPool(poolSize);   // blocking client → own threads
}
public void asyncInvoke(Envelope in, ResultFuture<Envelope> rf) {
  CompletableFuture.supplyAsync(() -> call(in), executor)
      .whenComplete((res, err) -> rf.complete(
          err == null && res != null ? List.of(res) : List.of()));  // never completeExceptionally
}
  • unorderedWait vs. orderedWait: ordered mode holds each result until every earlier request has finished, so one slow call delays all the results behind it. Refreshes for different devices do not depend on each other, so unordered mode is the right choice here.
  • Capacity is the maximum number of requests in flight. When it is full, the operator applies backpressure. That keeps the external API from being flooded, but it also means a slow API slows down the whole job.
  • Async functions can't use keyed state. The keyBy before the async operator only spreads the work across subtasks. That is why the token is fetched in a separate keyed flatMap before this step.
  • Failure policy: calling completeExceptionally fails the task and restarts the job. Completing with an empty list drops only that record, and a success/failure counter tracks how often it happens.
Watch out for timeouts. If you don't override RichAsyncFunction.timeout(), an operator timeout completes the request exceptionally, and that restarts the job. Either set the HTTP client's timeout clearly below the operator timeout, or override timeout() to call rf.complete(List.of()) and increment a counter.

6 · Never throw from processElement

If processElement throws an exception, the task fails, the job restarts from the last checkpoint, and the same record is processed again. If the record is malformed, it will throw again every time. That is a poison pill: the job keeps restarting and never gets past that record. Every operator in this job uses the same structure: 

public void processElement(Envelope in, Context ctx, Collector<Envelope> out) {
  var span = Telemetry.start("staticDataProcessor", in.f0);
  try {
    process(in, ctx, out);
    successCounter.inc();
  } catch (Exception e) {
    failedCounter.inc();
    span.logException(e);
    ctx.output(DLQ, in);          // keep the record for auditing and replay
  } finally {
    Telemetry.finish(span);
  }
}

// job: merge every DLQ, spread evenly, one sink
staticOut.getSideOutput(DLQ).union(globalOut.getSideOutput(DLQ))
         .rebalance()
         .sinkTo(firehoseSink).uid("dlqFirehoseSink");
  • Errors in deserialization are handled the same way. A KafkaRecordDeserializationSchema receives a Collector, so a record that can't be parsed simply results in no output. The schema increments an invalid counter and does not throw.
  • Why rebalance()? DLQ traffic comes from whichever subtask failed, so it is uneven. Round-robin distribution spreads that load evenly across the sink's subtasks.
  • The exception is open(). If a database or HTTP client can't be created, it is better to throw a FlinkRuntimeException and fail immediately than to process records with a broken client.

7 · Settings that make the job operable

SettingWhat the job doesWhy
.uid() + .name()On every source, operator and sink, using values from one enumA stable uid is how savepoint state is matched to operators. Without one, the uid is derived from the graph shape, and adding a single source would break the restore.
Per-operator setParallelismSources: up to the partition count. Token cache / async / sinks: 1. Processors: full.Size each operator to its actual bottleneck: partitions, distinct keys, API rate limits.
setMaxParallelism(256)Set explicitlyThis is the number of key groups, and it can never change after state exists. It is the upper limit for rescaling.
