Connectors Lab — Kafka vs Kinesis

Module 03 mentioned that a real source is usually "a Kafka topic, Kinesis stream, or similar" without saying much more. This lab makes that concrete: configure a real source connector of either kind, then watch Flink actually consume from it — partition by partition, or shard by shard.

New to this? Start here. Think of Kafka and Kinesis as two different shipping companies that can deliver events to your Flink job's loading dock. Same kind of package (events), different trucks and paperwork: Kafka splits a topic into partitions, Kinesis splits a stream into shards — but both exist for the same reason: so many parallel subtasks (Module 02) can consume at once instead of everything queuing behind one reader.

Same idea, different vocabulary

ConceptKafkaKinesis
The stream of eventsTopicStream
A parallel slice of itPartitionShard
"How far have I read?"OffsetSequence number
Where to connectBootstrap serversRegion + stream ARN
Replay everything?earliestTRIM_HORIZON
Skip the backlog?latestLATEST

The mapping isn't a coincidence — both are solving the same problem (an ordered, replayable, partition-parallel log), just with different names and different operational models (Kafka: you usually run/manage the cluster; Kinesis: AWS manages it).
