Module 04

Time & Windows

Streams are unbounded, so aggregations need a way to carve them into finite chunks. That's what windows do — and knowing which clock you're measuring against is what makes windows behave correctly.

Three notions of time

TimeMeaning
Event timeWhen the event actually happened, per a timestamp in the data itself. Correct even if events arrive late or out of order.
Ingestion timeWhen the event entered Flink. A middle ground — stable, but not the true origin time.
Processing timeThe system clock of the machine doing the processing, at the moment it processes the event. Simplest and fastest, but not reproducible.

Most real applications use event time, because network delays and retries mean "when it arrived" is not "when it happened."

Watermarks: how Flink knows "we're caught up"

With event time, Flink can't just wait for a window to "run out" — events for it might still be in flight. A watermark is a moving marker in the stream: watermark W asserts "no more events with timestamp < W should arrive." When the watermark passes a window's end, that window fires. Events that still arrive after that (later than the watermark allowed for) are late.

Watermark walkthrough

Bounded out-of-orderness watermark, allowing events up to 2s out of order: watermark = maxEventTimeSeen − 2. Step through events as they arrive (not necessarily in event-time order).

Window types

  • Tumbling — fixed-size, non-overlapping, back-to-back. Every event belongs to exactly one window.
  • Sliding — fixed-size, but a new window starts every "slide" interval, so windows overlap and an event can belong to several.
  • Session — no fixed size; a window closes after a gap of inactivity, so it captures bursts of activity.
