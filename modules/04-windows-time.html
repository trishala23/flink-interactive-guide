Module 04

Time & Windows

Streams are unbounded, so aggregations need a way to carve them into finite chunks. That's what windows do — and knowing which clock you're measuring against is what makes windows behave correctly.

New to this? Start here. Picture water flowing continuously out of a tap — it never stops, so "what's the total amount of water?" is a question with no answer yet. But if you hold a bucket under it for exactly 10 seconds, you get a real, useful number: "2 liters in this 10-second bucket." A window is that bucket — a way to catch a slice of an endless stream so you can ask "how many orders in the last 5 minutes?" instead of the unanswerable "how many orders ever?"

Why does this need three different clocks?

Say someone plays a mobile game on a train, scores a point at 2:00:00pm, but the phone loses signal and that score only reaches Flink's servers at 2:00:05pm, five seconds later. Which time should "count" for that point — 2:00:00 or 2:00:05? That five-second gap is exactly why Flink lets you pick between three clocks:

ClockIn plain wordsExample
Event time The time stamped on the event itself, from wherever it happened — like the postmark on a letter, not the day it lands in your mailbox. Correct even if the event shows up late. The game point above always has event time 2:00:00pm, no matter how late it arrives at Flink.
Ingestion time The moment the event walks in Flink's door. A middle ground — more stable than processing time, but still not the event's true origin. Flink stamps the point 2:00:05pm, the instant it actually receives it.
Processing time Whatever the server's clock happens to read the moment it gets around to handling the event. Simplest and fastest, but re-running the same data can give different results. If the server is briefly overloaded and only processes the point at 2:00:07pm, that's its processing time — two seconds later than ingestion, for no meaningful reason.

Most real applications use event time, because network delays and retries mean "when Flink saw it" is not the same as "when it actually happened" — and for most questions you care about (like a leaderboard, or "orders in the 2pm hour"), the real happened-at time is the one that should count.

Watermarks: how Flink knows "we're caught up enough"

Here's the catch with event time: Flink can't peek into the future to know whether every 2:00pm-ish event has arrived yet — some could still be stuck in transit. So Flink needs a policy for deciding "I've waited long enough, let's close this window and move on" — the same way a teacher might wait a minute after the bell for stragglers, then start class anyway rather than waiting forever for someone who might not show up at all.

That policy is a watermark — a moving marker Flink attaches to the stream. Watermark W is Flink saying "I'm now assuming no more events with timestamp before W are coming." Once the watermark passes a window's end time, that window fires (produces its result). Any event that still shows up after that — later than the watermark allowed for — is officially late.

The trade-off: wait longer before declaring a window "done," and you catch more stragglers but delay every result. Wait less, and results come faster but you risk missing events that were genuinely just running late. There's no watermark setting that's free of this trade-off — you're always choosing how patient to be.

Three shapes of bucket

Same "bucket catching water" idea from above, but three different ways to hold the bucket:

TypeIn plain wordsEveryday example
Tumbling Fixed-size buckets, back-to-back with no gaps and no overlap. Every event lands in exactly one bucket. Splitting your day into fixed meal slots — breakfast 7–9am, lunch 12–2pm. Any given moment belongs to exactly one slot (or none).
Sliding Same fixed bucket size, but a new bucket starts every few seconds instead of only when the last one ends — so buckets overlap, and one event can land in several. A weather app showing "rainfall in the last hour," refreshed every 10 minutes. Each new number overlaps almost all of the previous one.
Session No fixed size at all — a bucket just stays open as long as events keep arriving, and closes once there's a gap of inactivity. A Netflix "watch session": keep pressing play within a few minutes of each episode ending and it's still one session; walk away for an hour and your next episode starts a new one.

How this is actually used in Flink

Windows almost always follow a keyBy (Module 03), so each key gets its own independent buckets. A real example: an online store wants "total sales per product, every 5 minutes" for a live dashboard — not one grand total since the store opened. 

orders
    .keyBy(order -> order.productId)
    .window(TumblingEventTimeWindows.of(Time.minutes(5)))
    .sum("amount")
    .sinkTo(dashboardSink);

This is the same keyBy(...).sum(...) shape from Module 03 — the only new piece is .window(...) sitting in between, which is what turns "running total forever" into "total for this 5-minute bucket, then start fresh."
