Module 07

Deployment & Operations

The same job can run in very different environments. Picking the right one is mostly about who owns the cluster's lifecycle and how much isolation your jobs need from each other.

New to this? Start here. Remember Module 02's restaurant kitchen (JobManager = manager, TaskManagers = cooks)? This module is really just: where does that kitchen live? Do you build your own kitchen from scratch? Rent space in a shared commercial kitchen alongside other chefs? Book a private pop-up kitchen for just one event? Or order from a ghost-kitchen service where someone else already runs everything? Same trade-offs, just for compute clusters instead of kitchens.

Why does this choice even matter?

Two things pull in opposite directions: efficiency (not wasting time or money spinning up infrastructure) and isolation (one job's problem not becoming everyone's problem). Run every job in its own brand-new cluster, and you're maximally isolated but paying a setup cost every single time. Cram every job into one shared, always-on cluster, and startup is instant — but now if that cluster's manager crashes, every job on it is affected at once, not just the one that caused the problem. Every option below is a different point on that same trade-off.

Cluster lifecycles — the shape of the kitchen booking

  • Session cluster — like a shared commercial kitchen, always open, used by many chefs (jobs) throughout the day. Efficient — no setup wait — but everyone using it shares its fate: if the kitchen loses power (the JobManager crashes), every chef currently cooking there is affected, not just one.
  • Application cluster — like booking a private pop-up kitchen for exactly one event, torn down once it's over. Nobody else's problems can leak into your event. This is the standard recommendation on Kubernetes.
  • Per-job cluster — the same private-kitchen idea, just booked by a client from outside rather than baked into the event's own setup; increasingly replaced by application mode on newer resource managers.

Where the kitchen actually sits

TargetIn plain words
StandaloneYou build the kitchen yourself — run JobManager/TaskManager processes by hand, with nothing automatically managing them. Full control, but every bit of setup and monitoring is on you.
KubernetesA modern, flexible facility that can add or remove kitchen space on demand. The recommended target today, especially via the Flink Kubernetes Operator, which automates upgrades and resizing for you.
YARNWhatever facility your company already built, if it's a Hadoop-based one — Flink just requests space (containers) from YARN's existing resource manager.
Managed servicesA ghost-kitchen service (e.g. Amazon Managed Service for Apache Flink, Ververica Platform) — someone else owns and runs the kitchen entirely; you just hand them your job.

Scaling and upgrades — changing the recipe without losing the kitchen

Say you need more cooks (higher parallelism) or a bug-fixed recipe (new job code) — but you don't want to throw away everything already cooking (the job's state). The pattern is always the same: take a savepoint (Module 05, the manual "save" before something risky), stop the job, then restart it from that exact savepoint with the new parallelism or code. The Flink Kubernetes Operator and the Application Mode upgrade flow automate this stop-save-restart sequence for you.

Watching a running job

The Flink Web UI (served by the Dispatcher, from Module 02) is your window into the kitchen while it's running: jobs in progress, the operator graph, and checkpoint history. Two signals there matter more than the rest, because they're usually how you first notice something's wrong — and they're closely related to each other.

Backpressure — a slow step forcing everyone upstream to slow down

Picture a busy kitchen line: if the cook plating dishes is slow, the cooks before them can't hand off finished food fast enough either — they're forced to slow down too, all the way back up the line, the same way a slow cash register backs up an entire checkout queue behind it. That's backpressure: when one operator can't keep up, every operator feeding it is forced to slow down to match, rippling backward through the whole pipeline.

This isn't a bug — it's Flink deliberately choosing to slow down rather than either dropping data or letting an overloaded operator's memory balloon out of control. The trade-off is that a slowdown anywhere becomes a slowdown everywhere upstream of it, including all the way back to the source.

QuestionAnswer
What usually causes it? One operator doing something expensive per record (a slow external API call, heavy computation), data skew (one key gets far more traffic than others, overloading a single subtask while others sit idle), or a slow sink (e.g. a struggling database on the other end).
Where do you see it? The Flink Web UI flags the specific operator that's "busy" (spending its time actually processing, unable to keep up) directly in the job graph — you don't have to guess which step is the bottleneck.
How do you fix it? Once you know which operator is the bottleneck: give it more parallelism (Module 02's slots), fix key skew so work is spread more evenly, or speed up/scale whatever slow external system it's waiting on.

Consumer lag — how far behind the source you are

If your source is Kafka, think of new messages arriving as a stack of incoming orders piling up at the kitchen door. Consumer lag is simply the size of that pile: how many messages (or how much time) sit between the newest message Kafka has and the last one your job has actually finished processing. Zero lag means you're caught up to the present moment; growing lag means you're falling further behind it.

QuestionAnswer
Is some lag normal? Yes — brief lag after a burst of traffic, or right after a job restarts and has a backlog to replay, is expected and should shrink back down on its own as the job catches up.
When is it a problem? When it keeps climbing instead of holding steady or shrinking — that means your job's throughput has fallen below the rate new messages arrive, so it will never catch up on its own, and every result gets staler the longer it goes on.
Where do you see it? Flink exposes it directly as a source metric (records/time behind the latest offset); Kafka itself also tracks it per consumer group, visible via tools like Kafka's own consumer-group CLI or a lag-monitoring exporter feeding your dashboards.
These two are usually connected. Say a fraud-detection job (Module 05) posts an alert to a Slack webhook for every flagged transaction. If Slack's API gets slow one day, the sink operator can't keep up — it starts backpressuring the operators before it, which backpressure those before them, all the way to the Kafka source, which is now forced to consume more slowly than messages are arriving. The Web UI would show the sink as "busy," and your dashboards would show consumer lag climbing — two symptoms of the exact same root cause. When you see rising lag, the Web UI's backpressure view is usually where you find out why.

For long-term monitoring (not just "what's happening right now"), Flink's metrics system exports both of these — plus checkpoint duration and failure rate (is the safety net still working?) — to Prometheus, Datadog, Graphite, and others, so you can alert on them before a user notices anything's wrong.
