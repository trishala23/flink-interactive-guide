Module 07

Deployment & Operations

The same job can run in very different environments. Picking the right one is mostly about who owns the cluster's lifecycle and how much isolation your jobs need from each other.

Cluster lifecycles

  • Session cluster — one long-lived cluster accepts many jobs over time. Efficient (shared resources, fast job startup) but jobs share fate: a JobManager crash can affect the whole session.
  • Application cluster — a cluster is started for exactly one application/job and torn down when it finishes. Better isolation, the standard recommendation on Kubernetes.
  • Per-job cluster — similar idea, submitted from a client rather than the image itself; deprecated on some resource managers in favor of application mode.

Where it runs

TargetNotes
StandaloneYou run JobManager/TaskManager processes yourself. No resource manager integration — full control, more manual ops.
KubernetesNative Kubernetes deployment (recommended) or via the Flink Kubernetes Operator for lifecycle management, upgrades, and savepoint-based rescaling.
YARNCommon in existing Hadoop ecosystems; Flink requests containers from YARN's ResourceManager.
Managed servicese.g. Amazon Managed Service for Apache Flink, Ververica Platform — someone else runs the cluster; you submit jobs.

Scaling and upgrades

To change parallelism or deploy new job code without losing state, take a savepoint (Module 05), stop the job, then restart it from that savepoint with the new parallelism or JAR. The Flink Kubernetes Operator and tools like the Application Mode upgrade flow automate this sequence.

Watching a running job

The Flink Web UI (served by the Dispatcher) shows running/completed jobs, the operator graph, backpressure, and checkpoint history. For long-term monitoring, Flink's metrics system exports to Prometheus, Datadog, Graphite, and others — the key metrics to alert on are checkpoint duration/failure rate, consumer lag, and backpressure.
