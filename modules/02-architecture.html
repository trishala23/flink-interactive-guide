Module 02

Architecture & Runtime

Every Flink job runs across a small set of cooperating processes. Understanding what each one does makes debugging, scaling, and deployment decisions much less mysterious.

New to distributed systems? Start here. Think of a Flink cluster like a restaurant kitchen. You (the Client) place an order at the front desk (the Dispatcher), which calls over a manager for your order (the JobManager). The manager checks with the staffing coordinator (ResourceManager) for free cooks, then hands the work to actual cooks standing at cooking stations (TaskManagers with task slots). Keep this picture in mind — every term below maps onto it.

How a job actually runs

Same five steps, first in plain English, then with the real term in parentheses:

  1. You run your program (a JAR, a Python script, or a SQL statement). This sends it to the front desk of the cluster (the Dispatcher).
  2. The front desk calls over a dedicated manager just for your job (starts a JobManager), which turns your code into a step-by-step plan (a JobGraph — the DAG of operators).
  3. The manager asks the staffing coordinator (ResourceManager) for enough free workers (task slots on available TaskManagers).
  4. Once workers are assigned, your pipeline's steps start running in parallel across those workers (deployed as subtasks in slots), and data starts flowing between them.
  5. The manager keeps watching the whole time — taking periodic snapshots (checkpoints) and restarting anything that crashes (see Module 05), so you don't have to babysit it.

Parallelism and slots, with real numbers

Each TaskManager (worker) is cut up into a fixed number of task slots — think of a slot as one cooking station: exactly one instance of one part of your pipeline runs there at a time. More slots means more copies of your pipeline can run side by side, which is what "parallelism" means.

Worked example: say you have 3 TaskManagers, each offering 3 slots (matching the diagram above) — that's 3 × 3 = 9 slots in the whole cluster. If you set your job's parallelism to 4, Flink runs 4 parallel copies of each operator, using 4 of those 9 slots, spread across whichever TaskManagers have room. You could run two such jobs (using 8 of 9 slots) — but a third job asking for 4 more would have to wait, because only 1 slot is left.

Rule of thumb: total slots in a cluster is the hard ceiling on how much parallelism a job can use at once. If a job asks for more parallel slots than the cluster has, it simply won't start until enough are free.

Deployment shapes

The diagram above shows a session cluster — one long-lived set of JobManager/TaskManagers running multiple jobs. Flink also supports application clusters (one cluster per job, useful in Kubernetes) and per-job clusters. Module 07 covers when to reach for each.
