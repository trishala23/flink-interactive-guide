Architecture & Runtime

Every Flink job runs across a small set of cooperating processes. Understanding what each one does makes debugging, scaling, and deployment decisions much less mysterious.

How a job actually runs

  1. You submit a job (a JAR, a Python script, or a SQL statement) to the Dispatcher.
  2. The Dispatcher starts a JobManager for that job, which turns your program into a JobGraph — the DAG of operators.
  3. The JobManager asks the ResourceManager for task slots on available TaskManagers.
  4. Once slots are allocated, operators are deployed as parallel subtasks across those slots, and data starts flowing between them.
  5. The JobManager coordinates checkpoints, tracks progress, and handles failures by restarting affected subtasks (see Module 05).

Parallelism and slots

Each TaskManager is divided into a fixed number of task slots — the unit of resource isolation. A pipeline with parallelism 4 runs 4 parallel instances of each operator; Flink packs them into slots across the TaskManagers you have available. More slots (more TaskManagers, or more slots per TaskManager) means more parallel capacity.

Rule of thumb: total slots in a cluster is the hard ceiling on how much parallelism a job can use at once. If a job asks for more parallel slots than the cluster has, it simply won't start until enough are free.

Deployment shapes

The diagram above shows a session cluster — one long-lived set of JobManager/TaskManagers running multiple jobs. Flink also supports application clusters (one cluster per job, useful in Kubernetes) and per-job clusters. Module 07 covers when to reach for each.
